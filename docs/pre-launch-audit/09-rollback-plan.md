# 09 — خطة التراجع | PRE-LAUNCH-AUDIT-001

## الإصدار السابق المستقر

- الفرع الأساس: `main` عند نقطة ما قبل دمج هذا التدقيق (آخر دمج موثّق عند بدء التدقيق: PR #575 وما قبله على `main`).
- على Vercel: أعد نشر **Deployment** السابق الناجح من لوحة المشروع (Instant Rollback).

## طريقة إعادة النشر

1. Vercel → Project → Deployments → اختر آخر نشر أخضر قبل الإطلاق → Promote / Rollback.
2. أو: `git revert` لدمج PR التدقيق ثم ادفع إلى `main` إن كان الخلل من التغييرات الجديدة فقط.

## التراجع عن migration

- Migrations الحصّة/النقاط **إضافة أعمدة** غالبًا — التراجع الآلي غير ضروري إن لم تُكسر القراءة.
- إن migration كسرت الإنتاج: استعد من نسخة Neon Point-in-Time / snapshot؛ لا تحذف أعمدة عليها بيانات مستخدمين دون موافقة.
- الحالات غير القابلة للتراجع الآلي: تفعيل اشتراكات خاطئة، حذف بيانات، تغيير أدوار جماعي.

## حفظ بيانات ما بعد الإطلاق

- قبل استعادة DB كاملة: صدّر جداول `users` الجديدة، `chat_conversations`/`messages`، `attachments` metadata التي أُنشئت بعد الإطلاق.
- فضّل rollback التطبيق مع الإبقاء على DB إن كان الخلل في الواجهة فقط.

## متى يجب التراجع فورًا

- تعطل تسجيل الدخول للجميع
- تسرّب بيانات مستخدم لمستخدم آخر (IDOR)
- خصم حصّة/مالي واسع خاطئ
- فشل جوهري في قاعدة البيانات
- ارتفاع مستمر لأخطاء 5xx
- ثغرة أمنية حرجة مكتشفة بعد النشر

## المخوّل بقرار التراجع

- مالك المنصة / المسؤول التقني المعيَّن في قائمة الإطلاق (يُحدَّد قبل النشر).
