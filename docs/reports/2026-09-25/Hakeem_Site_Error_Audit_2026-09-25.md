# تقرير تدقيق أخطاء موقع حكيم

تاريخ التدقيق: 25 سبتمبر 2026  
الحالة: تدقيق تشخيصي فقط. لم يُعدَّل الموقع، ولم تُعدَّل قاعدة Neon أو Supabase، ولم تُكشف أي قيمة سرية في هذا التقرير.

## خلاصة تنفيذية

التدقيق أثبت وجود أعطال إنتاج حقيقية وليست مجرد مشكلة عرض:

| الأولوية | العدد | الخلاصة |
|---|---:|---|
| P0 عاجل | 4 | صفحة الأنظمة العامة تتعطل، عدم توافق دور قاعدة البيانات، مهلات MCP، ومنطق استرداد المالك غير الآمن |
| P1 مرتفع | 3 | مادة رقم 0 في البيانات، عمليات DDL أثناء الإقلاع، وفجوة عرض الأحكام |
| P2 متوسط | 7 | إعداد Next غير صالح، إخفاقات Preview سابقة، تحذير bcrypt، مراقبة أحكام ناقصة، ومفتاح MCP في الرابط |
| P3 منخفض | 3 | favicon مفقود، تحذيرات lint، واعتماد على catch صامت |

أخطر ترتيب إصلاح:

1. أوقف أو أصلح مسار كلمة مرور المالك المضمّنة قبل تطبيق هجرة دور SUPER_ADMIN.
2. أصلح BASE في صفحة النظام القانونية وانشر Preview للتحقق.
3. طبّق هجرة enum إلى Neon بعملية مستقلة ومراجعة، لا ضمن build Vercel.
4. عالج مهلات MCP وعمليات DDL في instrumentation.
5. نظّف سجل المادة رقم 0 بعد فحصه قراءةً فقط.

## النطاق والمنهج

شمل التدقيق:

- سجل أخطاء Vercel للإنتاج خلال آخر 7 أيام.
- سجل بناء Vercel للإنتاج وثلاثة Deployments Preview فاشلة.
- فحص الصفحات العامة: الرئيسية، قائمة الأنظمة، نظام الشركات، مادة 1، التوثيق، وواجهات المطورين.
- مراجعة المصدر في commit الإنتاج a6910138dc7452c89165ebb2ec7c397cec31adbd وفي main الحالي.
- فحص محلي: Prisma generate، TypeScript، lint، security scanner، وNext build.

لم يشمل التدقيق:

- تسجيل الدخول بحساب حقيقي أو اختبار صلاحيات مستخدم مسجّل.
- قراءة مباشرة محمية من قاعدة Neon أو تغيير أي سجل فيها.
- كشف متغيرات Vercel أو كلمات المرور أو مفاتيح API.
- زحف كامل لكل رابط أو كل API في المنصة.

لذلك فعبارة "كافة الأخطاء" هنا تعني: جميع الأخطاء التي أمكن إثباتها ضمن هذا النطاق، مع فصل واضح بين العطل المؤكد والخطر الذي يحتاج تحققًا إضافيًا.

### DB-001 — دور SUPER_ADMIN موجود في Prisma وغير موجود في Neon

الأولوية: P0  
الحالة: مؤكد في سجلات الإنتاج  
الأثر: فشل تجهيز حساب المالك عند تشغيل الدوال، وتلوث السجلات بأخطاء Prisma متكررة.

الدليل:

- سجل الإنتاج: invalid input value for enum UserRole: SUPER_ADMIN، برمز PostgreSQL 22P02.
- prisma/schema.prisma يعرّف SUPER_ADMIN.
- توجد هجرة prisma/migrations/20260723160000_add_super_admin_role/migration.sql لإضافة القيمة.
- سكربت build في commit الإنتاج لا يشغّل prisma migrate deploy.

الاستنتاج:

المصدر سبق قاعدة Neon. وجود ملف الهجرة في المستودع لا يعني أنها طُبّقت على قاعدة الإنتاج.

إصلاح آمن:

1. لا تطبّق الهجرة منفردة قبل معالجة AUTH-001 أدناه.
2. خذ Snapshot أو Neon branch، ثم شغّل أولًا فحص قراءة فقط:

~~~sql
SELECT unnest(enum_range(NULL::"UserRole")) AS role;
SELECT * FROM "_prisma_migrations" ORDER BY finished_at DESC;
~~~

3. راجع حالة الهجرة، ثم طبّق migration المراجعة في نافذة صيانة مستقلة.
4. تحقق من أن تجهيز المالك لا يعيد تعيين كلمة مرور موجودة.

معيار القبول:

- يوجد SUPER_ADMIN داخل enum في Neon.
- لا يتكرر خطأ 22P02 في Vercel.
- يعمل تسجيل الدخول المعتاد عبر Clerk ولا تتغير كلمة مرور أي مستخدم بسبب الإقلاع.

المساهمات المرجحة التي يجب قياسها، لا افتراضها:

- عمليات بحث الأحكام والبحث الهجين بلا سقف زمني واضح لكل استعلام.
- تشغيل DDL عند الإقلاع كما في RUN-001.

الإصلاح:

- أعد نتائج خطأ متحكمًا بها أسرع من انتهاء Vercel، بدل انتظار 300 ثانية.
- اختبر أداة بحث أحكام، وأداة count_only، وأداة enumerate على بيانات كبيرة.

معيار القبول:

- طلب MCP ناجح ضمن حد زمني معلن.
- الطلب غير القابل للتنفيذ يرجع خطأ منظمًا خلال أقل من 20 ثانية.
- صفر مهلات 300 ثانية خلال 24 ساعة بعد النشر.

### AUTH-001 — كلمة مرور استرداد افتراضية مضمّنة وإعادة تعيين كلمة مرور المالك

الأولوية: P0 للإصلاح قبل أي ترحيل للدور  
الحالة: مؤكد في مصدر commit الإنتاج  
قابلية الاستغلال: مشروطة بتفعيل OWNER_EMERGENCY_LOGIN_ENABLED وOWNER_EMERGENCY_ALLOW_PRODUCTION؛ لم أتحقق من قيم المتغيرات.

الدليل:

- lib/modules/auth/ensure-owner.ts في commit الإنتاج يحتوي قيمة كلمة مرور افتراضية مضمّنة في المصدر.
- instrumentation.ts يستدعي ensurePlatformOwner عند تشغيل runtime.
- ensurePlatformOwner ينشئ hash جديدًا ثم يحدّث passwordHash للمستخدم الموجود.
- app/api/auth/owner-login/route.ts يقبل fallback لنفس القيمة الافتراضية، ولا يحتوي rate limiting على مستوى التطبيق.

الخطر:

إذا فُعّل مسار الطوارئ في الإنتاج، يمكن أن تتحول قيمة موجودة في المصدر إلى وسيلة دخول للمالك. كما أن تطبيق DB-001 وحده قد يجعل الإقلاع يعيد ضبط كلمة مرور المالك في كل تشغيل، وهو سلوك خطير حتى لو لم يكن مسار الطوارئ مفعلًا الآن.

الإصلاح الموصى به:

1. لا تسجل أي قيمة افتراضية في المصدر أو في التقرير أو في commit.
2. أزل OWNER_DEFAULT_PASSWORD نهائيًا.
3. لا تعدّل passwordHash لحساب موجود داخل instrumentation.
4. إن كانت Clerk هي طريقة الدخول الرسمية، أزل مسار كلمة المرور الطارئ أو اجعله عملية يدوية قصيرة العمر بمفتاح محفوظ خارج المصدر وبـ rate limit.
5. بدّل كلمة مرور المالك، ألغِ الجلسات القديمة، وراجع سجلّات الدخول قبل إتاحة طوارئ جديدة.
6. أضف فحص CI يفشل عند وجود password/token/secret literal في مسارات الخادم، لا API keys فقط.

معيار القبول:

- لا يوجد secret أو password literal في ensure-owner أو owner-login.
- الإقلاع لا يكتب passwordHash لمستخدم موجود.
- الوصول الطارئ معطل افتراضيًا ومغطى بـ rate limit واختبار.
- مراجعة يدوية تؤكد تدوير كلمة المرور والجلسات.

## أعطال البيانات والاعتمادية

### DATA-001 — سجل مادة رقم 0 ظاهر في التنقل

الأولوية: P1  
الحالة: مؤكد من سلوك الإنتاج ومصدره  
الأثر: صفحة المادة 1 من نظام الشركات تعرض رابط "المادة ٠"، بينما فتح الرابط يعرض صفحة غير موجودة.

الدليل:

- اختبار المتصفح على /legal/نظام-الشركات/1 أظهر رابطًا إلى /legal/نظام-الشركات/0.
- فتح المسار 0 أعاد صفحة not-found داخل استجابة 200 من Vercel.
- كود الإنتاج لا ينشئ الرابط حسابيًا؛ بل يجلب المادة السابقة بشرط articleNumber أقل من 1. لذا الرابط يثبت وجود سجل مرتبط رقمه 0 في البيانات.
- Prisma يعرّف articleNumber كعدد صحيح بلا قيد يمنع الصفر أو القيم السالبة.

الإصلاح:

1. فحص Neon قراءة فقط:

~~~sql
SELECT id, "legalSystemId", "lawName", "articleNumber", title, "createdAt", "updatedAt"
FROM legal_articles
WHERE "articleNumber" <= 0
ORDER BY "lawName", "articleNumber";
~~~

2. راجع أصل كل سجل قبل حذفه أو تصحيحه. لا تحذف تلقائيًا.
3. أضف حارسًا في استعلامات العرض لاستبعاد articleNumber أقل من أو يساوي صفر.
4. بعد تنظيف البيانات، أضف CHECK constraint عبر migration مدروسة، ثم تحقق من عدم وجود سجلات مخالفة.

معيار القبول:

- لا يظهر رابط إلى مادة 0 أو سالبة.
- مسار المادة 1 لا يملك رابطًا سابقًا إن لم توجد مادة صحيحة قبله.
- نتيجة الاستعلام أعلاه فارغة بعد موافقة مالك البيانات على المعالجة.

### RUN-001 — تعديل مخطط قاعدة البيانات عند إقلاع الدالة

الأولوية: P1  
الحالة: مؤكد من instrumentation.ts ومن سجلات التشغيل  
الأثر: تأخير، احتمالات أقفال في Postgres، وصعوبة تتبع حالة المخطط.

الدليل:

- instrumentation.ts ينفذ ALTER TABLE وCREATE INDEX.
- ثم يشغل ensureConversationSessionSchema وensureAiUsageSchema وensureBlueprintSchema وensureDocToolSnapshotSchema.
- سجل Vercel يعرض رسائل "مخطط ... جاهز" مع طلبات الصفحات.

المشكلة:

تشغيل DDL في serverless runtime يجعل صحة الطلب العام مرتبطة بمهام بنية تحتية، ويزيد احتمال التأخير وسباقات التشغيل. لا يكفي أن تكون الجمل idempotent.

الإصلاح:

- نقل DDL إلى migrations أو workflow إداري صريح.
- جعل instrumentation يحمّل الإعدادات أو يتحقق قراءةً فقط.
- إن لزم فحص صحة، اجعله health/readiness يقرأ المخطط بدل تغييره.

معيار القبول:

- لا تظهر رسائل schema-ready في كل تشغيل دالة عام.
- لا يوجد ALTER أو CREATE داخل instrumentation في مسار الإنتاج.
- ترحيلات قاعدة البيانات مسجلة ومراجعة وقابلة لإعادة التشغيل بشكل مضبوط.
