# مواءمة وحدات الاستخدام v2

## نتيجة المقارنة

كان المشروع يضم نظامين قائمين:

- `freeQuota*`: حصّة بعدد الاستخدامات، افتراضيًا 20.
- `creditsBalance` و`credit_transactions`: نقاط ولاء وتحفيز وصرف محتوى.

حُفظ النظامان دون حذف أو تحويل أرصدة. أضيفت وحدات الاستخدام بوصفها رصيد الخدمات
الذكائية، لأن تحويل نقاط الولاء القديمة إلى وحدات كان سيغيّر قيمة أرصدة المستخدمين.

## ما أضيف

- 100 وحدة تجريبية موزعة: 25 بعد توثيق الجوال مع البريد الموثق بالمصادقة، 50 بعد
  إكمال الملف، و25 بعد أول مستند يصل إلى `READY`.
- إحالة مؤهلة بعد التوثيق والملف وأول استخدام ناجح أو مستند جاهز: 25 للمدعو و50
  للداعي، ثم 100 للداعي بعد أول شراء موثّق من webhook.
- تخزين `milli-units`: كل 1000 جزء = وحدة واحدة ≈ 1000 توكن موزون.
- Ledger إضافي فقط، سلسلة SHA-256، ومشغّل PostgreSQL يمنع UPDATE وDELETE.
- حجوزات 15 دقيقة، تسوية ذرية قابلة لإعادة الطلب، وتحرير عند النتيجة المحجوبة.
- أسعار OCR والفهرسة والبحث الهجين وreranking والباقات والحصص.
- ربط البوابة المركزية مع اسأل حكيم والاستشارات والقاضي التفاعلي، وربط رفع المستند.
- API حساب، سجل ومصدر كل حركة، ولوحة سوبر أدمن للتفعيل والأسعار والباقات والتعديل
  اليدوي مع Audit Log.

## رولأوت بلا كسر

1. تطبيق الهجرة `20260729130000_usage_credits_v2` في staging.
2. إبقاء `usage_credits_v2=false`؛ يستمر النظام القديم كما هو.
3. فتح صفحات الحساب والإدارة للتحقق من منح المكافآت المستحقة idempotently.
4. اختبار الاستهلاك المتزامن والحجز والفشل وwebhook الدفع.
5. تفعيل العلم لمجموعة داخلية، ثم توسيعه بعد مراقبة Ledger.

## حدود متبقية

- مسار OCR في منصة الوثائق مستقل وغير مربوط بمستخدم مصادق حاليًا؛ لم يُحجب أو
  يُغيّر. التسعير جاهز، والربط ينتظر إسناد العملية إلى `userId`.
- لا توجد عملية فهرسة خلفية ترفع المرفق إلى `READY` في مسار الرفع الحالي؛ مكافأة
  أول مستند لن تُمنح قبل وجود نجاح فهرسة حقيقي، وهذا مقصود لتجنب منح صوري.
- لا تُطبّق الهجرة ولا يُفعّل العلم ضمن build أو deploy.
