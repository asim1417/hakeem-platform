# PR-1 — توجيه OCR على مستوى الصفحة + كاشف الفساد الدلالي العربي

مرجع الأمر: HKM-DOCUMENT-INTELLIGENCE-006 (§6، §11، §19، §23، §25)
الفرع: `claude/arabic-document-processing-vaqc31`
الحالة: مسودّة — **لا نشر إنتاجيّ، لا دمج تلقائيّ**. كل التغييرات خلف أعلام مطفأة افتراضيًا.

---

## المشكلة الجذر (قبل)

كان قرار «هل نستعمل OCR؟» يُتّخذ **على مستوى المستند** في مسارين:

1. المتصفح — `lib/modules/doc-tool/extract.ts:122`
   ```ts
   if (result.emptyPages >= result.pages || result.needsOcr) {
     return ocrPdf(fresh(), onProgress); // OCR لكل الصفحات في المتصفح (Tesseract)
   }
   ```
   نتيجةً لذلك: كتابٌ من 300 صفحة، صفحةٌ واحدة منه بطبقة نصّ معطوبة → **الكتاب كلّه**
   يُمسح ضوئيًّا في المتصفح. بطيءٌ جدًّا، ويُهدر طبقة النصّ الرقميّ السليمة لـ 299 صفحة.

2. الخادم (doc-node) — `services/doc-node/extract.ts`
   ```ts
   if (!processed.needsOcr) return { text: processed.body };
   throw new RemoteNeeded(...); // صفحةٌ واحدة معطوبة → الملف كلّه إلى Gemini
   ```

بالإضافة إلى صنفٍ من العطب لا تكشفه الكواشف القائمة: طبقة نصّ بحروف عربية **صحيحة
يونيكوديًّا** لكنّها تُشكّل كلماتٍ غير موجودة (خريطة ToUnicode معطوبة تُبدّل كل محرف
بآخر ثابت) — تمرّ كأنها نصّ عربيّ سليم فتُعرَض خربشةً بدل توجيهها إلى OCR.

وثالثًا: واجهة رفع الملفات في `DocToolApp` كانت تُعالج الدفعة بلا `try/catch` لكل ملف
(فشلُ ملفٍ يُسقط البقيّة)، وبإغلاقٍ قديم (`cloudHiQ` مفقود من مصفوفة التبعيّات).

---

## الحلّ (بعد)

### ① كاشف الفساد الدلالي العربي — `document-inspection/reshape.ts`
`arabicSemanticCorruptionScore(text)` جديد، مُضاف إلى **وحدة الكشف نفسها** (لا نواة موازية)
ومُدمَج في `cleanPdfTextLayer`. الإشارة الأقوى: انهيار **تغطية الكلمات الوظيفيّة وأداة
التعريف** — في العربية السليمة ~15–50٪، وفي النصّ المُبدَّل حرفًا بحرف ≈ 0٪. حتميّ،
يأخذ عيّنة (البداية/الوسط/النهاية) للمستندات الطويلة، ولا يُنذر على نصٍّ قصير أو غير عربيّ.

| المدخل | `structureCoverage` | `corrupt` |
|---|---|---|
| فقرة قانونية عربية سليمة | 0.49 | false |
| نفس الفقرة بإبدال حرفيّ ثابت | 0.00 | **true** |
| نصّ إنجليزيّ / قصير | — | skipped |

### ② توجيه OCR على مستوى الصفحة في المتصفح — `doc-tool/extract.ts`
خلف علم `NEXT_PUBLIC_HAKEEM_PAGE_LEVEL_OCR_V1` (مطفأ). يُعيد استخدام
`planPdfPageOcr` القائم: الصفحات النظيفة تُقرأ من طبقة النصّ، ولا يُرسَل إلى OCR إلا
الفارغة/المعطوبة/المُفسَدة دلاليًّا، ثم تُدمَج بـ `mergeScannedPages` برقم الصفحة.

### ③ صلابة رفع الملفات — `components/doc-tool/DocToolApp.tsx`
`try/catch` لكل ملف (فشلُ ملفٍ لا يُسقط الدفعة)، إصلاح إغلاق `cloudHiQ` القديم،
حارس `mountedRef` ضدّ تحديث الحالة بعد التفكيك، وعرض الأخطاء باسم الملف لا ابتلاعها.

### ④ توجيه OCR على مستوى الصفحة على الخادم — `services/doc-node/*`
خلف علم `HAKEEM_DOC_NODE_PAGE_LEVEL_V1` (مطفأ). `planPdfPagesNode` يصنّف كل صفحة؛
الحالة المختلطة تحمل الخطّة على `RemoteNeeded`، فيستخرج المُوزّع الصفحات المحتاجة فقط
كـ PDF أحاديّ الصفحة (`extractSinglePages`)، يقرأها Gemini متوازيةً بالجدولة المتكيّفة،
ثم يدمجها `mergePlanWithOcr` في محلّها برقم الصفحة.

- كل المسارات الجديدة **خلف أعلام مطفأة افتراضيًا**؛ السلوك القديم يبقى حرفيًّا عند الإطفاء.
- لا مفاتيح/أسرار في الكود أو السجلّات أو الواجهة. `qa:security` أخضر.

- لم يُرفع ملف الاختبار الخاص إلى المستودع (اختُبِر محليًّا فقط)؛ الاختبارات الآليّة تركيبيّة.

# PR-2 — ذاكرة القراءة الضوئية بمفتاح البصمة (تسريع مئات الصفحات)

الرافعة الثانية بعد توجيه الصفحة: **الصفحة نفسها لا تُقرأ ضوئيًّا مرّتين.**

## الفكرة
نحسب بصمة SHA-256 لبايتات صورة الصفحة المرسومة (حتميّة لنفس المحتوى)، ونخزّن ناتج
القراءة مفتاحًا بها. الصفحات المتطابقة تُستردّ فورًا بلا نداء Gemini:
- صفحاتٌ بيضاء/فاصلة متكرّرة
- ترويسات/أختام/تذييلات مكرّرة عبر الصفحات
- **إعادة رفع الملف نفسه** (السيناريو الأكبر: مراجعة الوثيقة مرّاتٍ)

## التطبيق
| الطبقة | الموضع | العلم |
|---|---|---|
| وحدة مشتركة | `document-inspection/ocr-cache.ts` (`hashBytes` + `MemoryOcrCache`) | — |
| المتصفح | `cloud-ocr.ts` → `cloudOcrPdfPages` | `NEXT_PUBLIC_HAKEEM_OCR_CACHE_V1` |
| الخادم | `doc-node/engines.ts` → مسار Gemini للصفحات | `HAKEEM_OCR_CACHE_V1` |

`MemoryOcrCache` محدودة الحجم (إخلاءٌ بترتيب الإدخال)، لا تخزّن فراغًا/إخفاقًا (فتُتاح
إعادة المحاولة)، وقيمُها نصٌّ مقروء فقط (لا بيانات خام). خطّاف بثٍّ `onPage(page, text)`
مُضاف للمكتبة (مختبَر) لعرضٍ تدريجيّ لاحقًا في الواجهة.

## التحقّق
- `test:document-inspection` **92/92** ✅ (+5 للبصمة والذاكرة) · `test:doc-node` 9/9 ✅
- `qa:security` أخضر ✅ · `next lint` بلا تحذيرات ✅ · `tsc` بلا أخطاء في الملفّات المتغيّرة ✅

## أثر السرعة المتوقّع (تراكميّ مع PR-1)
| الحالة | قبل | بعد |
|---|---|---|
| 500 صفحة رقميّة | ثوانٍ (PR-1) | ثوانٍ |
| إعادة رفع ملفٍ سبقت قراءتُه | قراءة كاملة | **فوريّة (كلّه من الذاكرة)** |
| وثيقة بترويسات/فواصل مكرّرة | كلّ صفحة نداء | الصفحات الفريدة فقط |

## التفعيل (PR-2)
```
NEXT_PUBLIC_HAKEEM_OCR_CACHE_V1=1   # المتصفح
HAKEEM_OCR_CACHE_V1=1               # الخادم
```

# PR-3 — عرضٌ تدريجيّ للنصّ أثناء القراءة السحابية

الرافعة الثالثة: تحسين **الإحساس** بالسرعة — أوّل صفحة تظهر في ثانية.

## الفكرة
عبر خطّاف `onPage` (المُضاف في PR-2)، تُعرض صفحات الـ PDF في المعاينة فور اكتمالها
بدل انتظار الوثيقة كاملةً. لا يتغيّر زمن المعالجة الكليّ ولا الناتج النهائيّ المحفوظ —
تحسينُ تجربةٍ فقط.

## التطبيق (خلف `NEXT_PUBLIC_HAKEEM_OCR_STREAM_V1`)
- `onPage` مُمرَّر عبر `ExtractOptions` → `cloudOcr` → `cloudOcrPdfPages`.
- معاينةٌ **عابرة** (`livePreview`) في `DocToolApp`: **لا تمسّ** مصفوفة الوثائق ولا منطق
  الإضافة الدفعيّة المُصلَّب في PR-1 (تصميمٌ منخفض المخاطر). تُبنى بترتيب الصفحات (البثّ
  متوازٍ فقد يصل غير مرتّب) وتُمحى عند اكتمال الدفعة فتحلّ الوثائق النهائيّة محلّها.
- محميّة بحارس `mountedRef`.

## التحقّق
- `tsc` بلا أخطاء في الملفّات المتغيّرة ✅ · `next lint` بلا تحذيرات ✅
- `test:document-inspection` 92/92 ✅ · `test:doc-node` 9/9 ✅ · `qa:security` أخضر ✅
- المنطق الواجهيّ (المعاينة العابرة) لا يمسّ مسارات مختبَرة؛ يستحقّ تحقّقًا بصريًّا عند التفعيل.

## التفعيل (PR-3)
```
NEXT_PUBLIC_HAKEEM_OCR_STREAM_V1=1
```
